## Purpose

Agentic PLC version: v1.13.0; Skill: plc-requirements-authoring; LLM: claude-opus-5-thinking; Timestamp: 2026-08-20T15:32:44Z; Input ref: NVRACKSTAT-52

The backend has **81 modules** calling `logging.getLogger` and **no central logging configuration
at all** — no `basicConfig`, no `dictConfig`, no `setLevel` anywhere under `backend/`. Every logger
therefore inherits whatever gunicorn leaves on the root logger, which means log level, format and
destination are not properties this product controls.

Separately, there is **no audit record of operator actions**. The nearest existing artifacts are
the AI-agent tool JSONL (`var/logs/agent_tool_audit.jsonl`) and the optional Parquet request
capture, neither of which answers the question every handover asks: *who did what, to which rack,
when, and what came of it.* The 2026-08-20 threat model records this as an open gap, and T-18
records sensitive `RACK_*` values reaching logs today.

This feature delivers the logging substrate and the audit trail. It is deliberately the phase
**before** identity (Phase 2) and authorization (Phase 3), because both of those need somewhere to
record their decisions, and the audit chokepoint built here is the same one Phase 3 will use to
evaluate authorization.

This is a draft working artifact. It does not replace canonical SRD, STP, TAVA, nSpect, or
release-gate evidence.

## Assumptions

1. Operators reach these deployments through an SSH tunnel, so the TCP peer address is normally
   loopback. No HTTP request header carries a client-supplied source IP; `X-Forwarded-For` is
   added by *proxies*, and SSH port forwarding is a TCP relay that adds nothing.
2. `principal` is populated from the best available source in this phase (shared token, PAM user,
   or `anonymous`). Phase 2 replaces that with an authenticated subject without changing the
   record shape.
3. Audit events are written locally. Shipping them to a SIEM is a deployment concern served by the
   syslog/network sink, not by this feature.
4. The existing 81 `logging.getLogger(__name__)` call sites are correct and must not be edited;
   configuration is applied centrally.

## Open Questions

1. ~~Should the syslog sink default to UDP or TCP?~~ **RESOLVED 2026-08-20 (feature lead).** UDP,
   because that is what syslog is; presenting a TCP variant would imply a delivery guarantee the
   transport does not offer. Durability is met by a different sink rather than by making syslog
   pretend: the rotating file on a fileshare, an export API, and later a cloud target such as AWS
   CloudWatch. Recorded as FR-2a below.
2. Retention and rotation policy for the audit JSONL — size-based rotation, or date partitioning
   with external cleanup? Proposed: date-partitioned files, no automatic deletion, since deleting
   audit evidence should be a deliberate operator act.
3. Should audit events also be pushed to the existing Parquet lake when it is enabled, or is the
   JSONL plus syslog sufficient? The lake already captures requests, so there is overlap to
   resolve rather than duplicate.
4. ~~Is a `read`-class action worth auditing at all?~~ **RESOLVED 2026-08-20 (feature lead).**
   Mutating actions and authentication events are audited by default; read-only requests are
   excluded unless explicitly enabled. Auditing every `/api/status` poll would bury the signal it
   exists to preserve. Recorded as FR-12, AC-23/AC-24.

### Decision 1 — the chokepoint is `after_request`, with one deliberate second call site

`after_request` is the only Flask hook that has both the outcome and the elapsed time, which
`result` and `latency_ms` require. `before_request` has neither; `teardown_request` does not receive
the response.

Verified rather than assumed: `after_request` **does** run for a request the auth gate refuses in
`before_request` (a 401 from the gate carries the security headers added in `after_request`), and
`request.endpoint` is already populated inside `before_request` — which the gate itself relies on
for its bypass check. So a refusal costs exactly the same path as a success, and FR-10 needs no
separate mechanism.

The one exception is structural, not incidental: `/ws/terminal` is answered by WSGI middleware
*above* Flask's router, so no Flask hook can observe it. That is why FR-10b exists and why
`api/terminal.py` calls `audit.emit()` directly from the refusal branch. Two call sites is the
honest minimum; adding a third would mean the chokepoint had failed.

### Decision 2 — `action` is a declared vocabulary, enforced by a decorator

**Superseded design (recorded, because the reasoning was wrong in a specific way).** The first
draft used `request.endpoint` on the grounds that it is machine-true, needs no registry, and is
"stable across refactors that keep URLs, guarded by `test_route_parity.py`". That last clause does
not hold. `test_route_parity.py` snapshots **URL paths and methods, not endpoint names**, so
renaming `api_gpu_reset_async` leaves every existing test green while silently changing the
`action` string in all subsequent audit records. For a trail whose value is longitudinal — what
happened to this rack over months — that severs history from the present with no signal anywhere.
An audit key must not be a refactorable identifier.

**Adopted design.** An action name is declared at the route, in a validated vocabulary of the form
`<service>[.<subservice>]:<verb>` — `rack.power:reset`, `fabric:drain`, `auth:login`. `service` is
the text left of the colon, so the field pair stays derivable from one declaration.

```python
@bp.route("/gpu-reset", methods=["POST"])
@action("rack.power:gpu_reset")
def api_gpu_reset_async(): ...
```

The decorator does **not** resolve its own endpoint name — it cannot, because blueprint
registration happens later. It attaches the declaration to the function; a `build_registry(app)`
call after blueprint registration walks `app.view_functions`, resolves endpoint → action, and is
where validation actually happens (FR-14a): a malformed name or a duplicate claim raises at
startup. This ordering is the non-obvious part of the implementation and the reason the registry
is a module rather than only a decorator.

**On the HTTP-verb question, measured rather than assumed.** Of 103 endpoints serving a mutating
method, exactly **two** serve more than one: `comments.api_comment_put` (PUT/DELETE) and
`vault.api_vault_nvftp_token` (PUT/DELETE/GET). A single name per endpoint is therefore correct for
101 of 103, and the per-method form is an escape hatch for the two, not the general case:

```python
@action(put="comments:update", delete="comments:delete")
```

Seven further endpoints mix a read method with a mutating one; those need no extra machinery,
because FR-12 already excludes reads by default and the resolver keys on `(endpoint, method)`.

**Why this does not duplicate Phase 3's registry — the objection inverts.** The decorator *is* the
registry, started early, and the split is clean along the axis that matters: the **name** is
code-adjacent and versioned with the code that implements it, while the **policy** attached to that
name is deployment-adjacent and belongs in catalog documents per `core-designs.mdc` §2. Phase 3
then writes policy against a vocabulary that already exists and is already known to be complete,
instead of inventing one and retrofitting 103 call sites under time pressure.

**What keeps it honest.** Two gates, because a vocabulary with gaps is worse than a derived name —
it looks curated while being partial. A coverage test asserts every mutating endpoint has a
declared action and fails the build otherwise (FR-14b); a snapshot test pins endpoint → action, so
changing a recorded action string becomes a reviewed diff rather than a side effect. The
enumerability that justified the endpoint approach is preserved: AC-8 still asserts the chokepoint
sees routes it was never told about, and the coverage gate is what makes "never told about" a
build failure instead of a silent hole.

**Cost, stated plainly.** 103 declarations across 38 `api/` modules, accepted deliberately at the
Step 5 gate so that no audit record ever carries a derived name and the trail has one shape from
its first day. There is no fallback path: an undecorated mutating route fails the build, which is
the only version of this that does not decay.

### Decision 2a — the sync/async/stream twins share one action, which forces a `variant` field

Drafting the vocabulary changed a requirement, which is the reason it was drafted before
implementation rather than during it.

Many endpoints are the **same operation reached by a different transport**: `/api/gpu-reset` and
`/api/gpu-reset-async`; `/api/tools/install-hpcx-workspace` and its `-stream` sibling;
`/api/run-sysinfo` and `/api/run-sysinfo-stream`. Seven of the fourteen `tools` endpoints are
`-stream` duplicates of the other seven. Treating each as a distinct action would be wrong twice
over: an auditor reading the trail would see two unrelated action names for one operator intent,
and — the serious half — Phase 3 policy would have to grant the same capability twice. Granting
`tools:install_hpcx` on the synchronous route and forgetting the streaming one is an authorization
bypass that reads as a complete policy. Collapsing the twins makes that class of gap unexpressible.

So an action name is **not** one-to-one with an endpoint: 105 mutating `(endpoint, method)` pairs
resolve to **89 distinct actions**. That directly contradicts the first form of FR-14a, which said
two endpoints claiming one name must fail startup. The rule is therefore sharpened rather than
dropped: endpoints may share an action name only when they declare **different variants**, and the
collision that fails startup is a repeated `(action, variant)` pair. A typo still fails; deliberate
aliasing is expressible; and the transport an operator actually used is recorded rather than
inferred.

```python
@bp.route("/tools/install-hpcx-workspace-stream", methods=["POST"])
@action("tools:install_hpcx", variant="stream")
def api_tools_install_hpcx_workspace_stream(): ...
```

`variant` values in use: `sync` (the default), `async`, `stream`, `legacy` (a compat route such as
`/api/multirack-jobs/<id>`, whose module is already documented as a shim), and `form` (the
browser-form `POST /logout` beside `POST /api/logout`).

Two observations recorded rather than resolved, because both are conservative as they stand:

- **Several `POST` endpoints are semantically reads** — `rack:uptime`, `diag:hw_check`,
  `fabric.imex:check`, `analytics:aggregate`, `logs:tail` — using `POST` only to carry a request
  body. FR-12 audits them as mutating. That is the right default: each one executes commands on the
  head node or a tray, so it is a privileged capability that Phase 3 will want to govern even though
  it changes no state. No exception list is introduced.
- **`validation` carries nine separately named runs** where one `validation:run` with a tool
  parameter would be tighter. They stay separate because Phase 3 policy will plausibly differentiate
  them — authorizing an operator to run NCCL is not authorizing them to run a multi-hour NeMo job on
  five racks — and because the catalog already treats each as its own `Tool` document.

### What gets audited

Default: any request whose method is `POST`, `PUT`, `PATCH` or `DELETE`, plus authentication
events. Excluded by default: `GET`, `HEAD`, `OPTIONS` (FR-12), and static-asset paths entirely, so
an asset request performs no config read, no stat and no audit write (NFR-2, AC-17).
`NVIS_AUDIT_READS=1` opts reads in.

### Meeting the latency budget (NFR-2a)

The 5 ms p95 budget is met structurally rather than by tuning. The handler is opened once at
configure time, so an emit is one `write` to an already-open file plus one JSON serialisation of a
~500-byte object. No configuration-ladder read, no `stat`, and no path resolution happen per event;
the resolved paths and the trusted-proxy list are captured at configure time. Static-asset requests
short-circuit before any of this (NFR-2). The flood guard is a dict lookup on a tuple key.

If measurement shows the budget missed, the fallback is a bounded in-process queue drained by a
single writer thread — deliberately *not* the starting design, because a queue introduces a way to
lose events on abrupt termination, which is the wrong trade for an audit trail.

### Event shape

Field set per FR-5, one JSON object per line, 502 bytes typical. Serialisation is the JSON encoder only, never a formatted string (NFR-10) — JSONL is line-oriented, so an unescaped newline in a client-supplied field would forge a whole event. `resource` carries the path without its query string (NFR-11). `principal` comes from the
session, never from a header (FR-9) — `X-Rack-Operator` stays display-only. In this phase the value
is the configured auth user or `anonymous`; Phase 2 substitutes an authenticated subject without
changing the shape.

### Security And PLC Implications

- Closes the threat model's recorded "no audit log of operator actions" gap, and T-18 (sensitive
  environment values reaching logs) via the redaction filter.
- Does **not** close the authorization gap. `decision` reads `not-evaluated` with `policy_engine: none`
  until Phase 3 supplies a real decision (NFR-13, from threat T-52): the field exists now so the record
  shape does not change later, but it must not claim an authorization decision that no engine made.
  Enforcement, when it arrives, cannot live at this chokepoint — `after_request` runs after the view
  has executed, so policy evaluated there would record denials for actions that already ran (T-62).
- Introduces one new durable artifact holding operator behaviour. It is owner-only on disk
  (NFR-4), and reading it without shell access is deferred to an authorized export endpoint after
  Phase 3 — authentication alone would let any operator read every other operator's actions.
- The flood guard is itself a security control, not an optimisation: without it a refusal loop
  evicts the evidence of that loop.

### Advisory Notes

- **Basis:** agent-authored advisory estimate. No SecNemo run backs these ratings.
- **Weighting.** Per the feature lead, this delta is weighted toward **policy evaluation** (T-62, T-64)
  rather than the action-name schema. That is the right emphasis: the vocabulary's grammar is not an
  attack surface, and T-63 is retained not as a schema threat but as a *coverage* control — the build
  gate is what stops a capability being governed on one route and ungoverned on its twin.
- **Escalation:** yes. This phase creates a new durable artifact holding operator behaviour and is the
  foundation of an authentication and authorization change, so the auth work as a whole warrants a
  full `nvsec-tava` / SecNemo TAVA at the gate rather than this advisory draft.
- **Coverage gaps / assumptions:** the SPA is not modelled (it neither reads nor writes audit records
  in this phase). Phases 2 and 3 are modelled only where Phase 1 constrains them — T-62 and T-64 are
  recorded now because the decisions that make them cheap or expensive are being made now. TLS,
  Origin policy and the WebSocket gate are already covered as T-1..T-48 in the system threat model
  and are not re-derived here.
- **Phase 3 engine shape — prior art the feature lead has already built.** A pydantic-validated
  policy document with a default-deny evaluator is a closer fit for this product than the Cedar
  binding named in the original plan, for three reasons that are properties of this repo rather than
  preferences: `pydantic` is already resolved in the dependency tree (via `mcp`), whereas `cedarpy`
  is a community binding with no AWS-maintained Python SDK; a schema expressed as pydantic models is
  validated at load time in the same idiom the catalog already uses for its documents; and the
  vocabulary this phase ships (`service[.subservice]:verb` plus `variant`) is exactly the request
  identifier such an evaluator matches on, so the two compose without an adapter. The cost is the
  loss of Cedar's formal semantics and policy-analysis tooling, which argues for keeping the
  interface Cedar-shaped and testing the evaluator against an explicit decision table. Recorded here
  as design input for Phase 3, not a decision.

### Resolved Design Points

Both settled by the feature lead at the Step 6 gate (2026-08-20); recorded here rather than deleted,
because each rejected the cheaper-looking option for a stated reason.

1. **Refusals are individual until the threshold; only the summary flushes lazily** — on the next `emit()` for that key, plus an `atexit` flush. The first T refusals for a key (T = `NVIS_AUDIT_FLOOD_THRESHOLD`, default 10) are written immediately, so a lone refusal never waits on a flush; only the collapsed remainder is deferred. This half was pinned after the test-plan verifier loop found that a buffer-from-first reading made a single refusal unobservable until process exit — and unobservable *at all* for a subprocess killed with SIGTERM, since `atexit` does not run.
   Rejected: a timer thread. The timer would deliver a summary promptly for a key that stops
   recurring, but it buys that with a background thread whose only job is to write audit records —
   a thread that can fail independently of the request path and whose failure is invisible. The
   `atexit` flush bounds the delay to process lifetime, and the deploy sequence recreates the
   container often enough that this is not an open-ended window.
2. **`latency_ms` comes from an independent timestamp set in `before_request`,** not from the
   existing `g._lake_t0`. Reusing the lake middleware's timer would make the audit trail's duration
   field silently absent or wrong wherever that optional feature is disabled — an audit field whose
   correctness depends on an unrelated feature flag is a field nobody can trust.

## Audit Volume And Retention Sizing

Measured, not estimated: a representative audit event carrying the full FR-5 field set serialises
to **502 bytes** as single-line JSON (369 bytes without `user_agent`, which is the widest single
field at ~133 bytes). Retention for the default budget, which is **20 MiB** — `maxBytes` 5 MiB with `backupCount` 3 keeps
four files, the active one included. An earlier version of this table said 15 MB by counting only the
three backups; the error was in the conservative direction, so the floor held with more margin than
claimed, not less.

The operator column is the one that was missing, and it is why FR-7b was reshaped. It assumes one
audited action per operator per minute over an eight-hour working day — 480 events per operator-day:

| Events/day | Operators at that rate | Scenario | Retention |
|---|---|---|---|
| 200 | ~0.4 | one operator, routine day | 208.9 days |
| 1,000 | ~2.1 | FR-7b's original stated basis | **41.8 days** |
| 2,400 | 5 | a small validation team | 17.4 days |
| 9,600 | 20 | the multi-tenant target | 4.4 days |
| 20,000 | ~42 | read auditing enabled, or a large team | 2.1 days |

So the original "~30 days at 1,000 events/day" was really "~30 days for about two operators". The
30-day floor survives to roughly three operators on a fixed 20 MiB budget, which is why the
requirement now derives bytes from the observed rate instead of asserting a constant.

A sustained refusal loop is the volume risk that matters here, and it is the local form of a
known cloud failure: when denied attempts are not recorded, a denial loop is invisible until
something else surfaces it (the canonical case being an S3 cross-region replication denial
discovered only via the bill). Recording refusals fixes the invisibility, but against a *bounded*
budget it introduces the mirror-image failure — the loop evicts the history rather than inflating a
bill, and again nobody notices until the evidence is wanted. FR-10a is what closes both: refusals
are recorded, and repeats are collapsed so they cannot consume the budget.

The 1,000/day row is the design point, and it is why read-only requests are excluded by default
(FR-12): the bottom row is what auditing `/api/status` polling costs. Mutating-action volume scales
with operator activity rather than cluster size, so a larger cluster does not shorten retention
proportionally — but a longer campaign with more operators does, which is what FR-7c exists for.
