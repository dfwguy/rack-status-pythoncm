This plan captures the verification scope for the feature described in
`.plc/briefs/launch-configuration-brief.md` (requirements r4, design r4, both approved). It maps
**54 requirements** (44 FR, 10 NFR) and **52 acceptance criteria** onto **42 test cases** across all
eight PLC test layers, and states what is deferred and what is out of scope.

This is written **before implementation**, so almost every `Test artifact` below names a test that
does not exist yet. That is the intended state, and it carries one obligation — see the artifact
note under *Test Cases*.

Three properties carry disproportionate weight, and each has a case whose absence would leave a
silent defect:

1. **The loader must run above the first first-party import, not merely before the bootstraps**
   (FR-3a). `config_env.py:737` snapshots `os.environ` at *import* and `config_env.py:769-773`
   **pops** any Settings-managed key missing from that snapshot, so a file-supplied value loaded too
   late is *deleted* mid-startup. TC-21 is the behavioural proof; TC-22 is the drift guard.
2. **`setdefault` is the precedence rule, and `""` is a value.** `_eget` returns
   `os.environ.get(name)` whenever it `is not None` (`config_env.py:915-917`), and the module's own
   header says so: "a blank overlay falls through, but `FOO=` in the process environment is an
   explicit empty value and wins" (`config_env.py:20-21`). TC-19 is written to fail on an
   `if not os.environ.get(k)` implementation and pass on `setdefault`.
3. **The runtime image is a third tree.** `Dockerfile:26` is `ubuntu:22.04` and `:34` installs
   `python3` (3.10.12, where `import tomllib` raises); every Python CI job is `python:3.12-slim`
   (`.gitlab-ci.yml:61,109,144`). So the fallback branch is dead code in every tree that runs the
   suite. TC-11 and TC-13 mask the module rather than depending on the interpreter; TC-39 asserts
   against the image itself.

It is a draft working artifact. It does not replace canonical STP, TAVA, Jenkins-validated results,
nSpect, or release-gate evidence.

## Entry Criteria

1. Requirements and acceptance criteria in the feature brief are approved — **met**: requirements
   milestone recorded at r2, refined and re-verified at r4.
2. Design components and interfaces are approved — **met**: r3 design approved by the feature lead
   conditional on the RG-1 fix, which landed in r4. RG-1 was the blocker for this document.
3. **`tomli` is pinned in `backend/requirements.txt` and installed in every test environment.**
   Not yet met, and it gates real cases rather than being paperwork: verified 2026-09-03 that
   `import tomli` fails in both the system interpreter and `.venv`, so TC-11 and TC-13 cannot pass
   until DC-8's pin lands and environments are reinstalled.
4. The `docker-save` CI job emits an image tarball (`--tarPath`) on the branch under test, or TC-38
   has nothing to inspect. `docker-build` uses `--no-push` and produces no artifact
   (`.gitlab-ci.yml:204-223`).
5. Test environments and fixtures listed in `Environments And Fixtures` are available or have a
   recorded plan to be available before execution.

## Exit Criteria

1. Every test case in this plan has been executed or has a recorded deferral reason.
2. Every acceptance criterion has at least one passing test case or a recorded deferral with an
   accepted reason.
3. `python -m pytest backend/tests/ -v` and `ruff check` both pass, and
   `backend/tests/route_snapshot.json` is unchanged — this feature adds no route (decision 8), so
   any movement in that snapshot is a defect.
4. **`test_config_precedence.py`, `test_config_materialize_hook.py` and `test_job_env_missing_file.py`
   are byte-identical to their base-commit blobs and green.** This is NFR-8's operative test: absent
   must mean *identical*, not *similar*. Editing one of those three to make this feature pass is the
   failure this criterion exists to catch.
5. `bin/check-tracked-tree.sh --with-tests` passes, and passes again with a 50-key `greenlight.toml`
   present in the tree (TC-42).
6. `bin/check-coverage-floor.py` reports every file this feature adds at or above 50%, measured in a
   tracked-only tree.
7. Verification evidence for executed cases has been logged via `plc-evidence-ingestion` against
   `FR-*` / `NFR-*` / `AC-*` refs and is referenced from the feature brief.
8. **TC-35 has actually run at least once**, with its p95 and its recorded baseline logged against
   `NFR-1` / `AC-29` on a named machine. Stated as a criterion because TC-35 is the only evidence
   for the Performance layer and is skipped on CI by design, so nothing else would notice it never
   executing.

## Coverage Gaps

All 54 requirements and all 52 acceptance criteria have at least one covering test case, and all
eight layers are covered. There is no requirement or AC with zero coverage.

Two cases are **partially** automatable, and the reason is the same in both: the pipeline cannot run
the built image. Recorded here rather than left implicit, because "automated test in CI" in the
brief reads as fully closed and it is not.

1. **AC-4a (TC-39) is automated against a *reproduced* interpreter, not the built image.** The k8s
   runners have no Docker daemon — the pipeline says so at `.gitlab-ci.yml:227`, which is why
   `docker-save` uses Kaniko `--tarPath` — and this criterion requires *executing* python3 inside
   the image. Arm (a) reproduces the runtime faithfully (`image: ubuntu:22.04`, the same
   `apt-get install python3` line as `Dockerfile:34`, the same pinned requirements) and runs on
   every pipeline; arm (b) is the literal in-image assertion and is a workstation demonstration.
   The residual risk is a Dockerfile change that alters the interpreter without altering arm (a) —
   e.g. a base-image bump or a `python3.11` package. **Proposed disposition:** accept the two-arm
   split for now, and file a follow-up to add a Docker-capable runner tag or a scheduled job that
   `docker load`s the `docker-save` artifact and runs arm (b) automatically. Reviewer approval
   needed on the residual.
2. **AC-1f (TC-38) is fully automated but by a different mechanism than the brief implies.** No
   daemon is needed because absence in an image is a property of its layers, so the assertion is
   tar-level. No residual risk, but it requires `docker-save` (or a new job) to run `--tarPath` on
   the branch under test — `docker-build` uses `--no-push` and leaves no artifact to inspect. This
   is entry criterion 4, not a gap in coverage.

## Open Questions

1. **Is `file` a provenance origin or a ladder rung, and does the plan's reading match the design's
   intent?** FR-25 says "the rung of the citizen-5 ladder that setting's effective value came
   from", but that ladder has **five** rungs (`config_env.py:16`, `:895-920`) and FR-11 explicitly
   forbids a sixth — while DD-6's closed vocabulary lists **six** values, adding `file`. This plan
   reads `env` and `file` as two *origins* at one rung, distinguished by DC-3's ledger, and TC-29 is
   written that way. It matters because the alternative reading ("make the ladder six-deep so
   `_eget` can report six rungs") satisfies AC-25 and violates FR-11, and it is the reading an
   implementer arrives at from FR-25's wording alone. Worth one sentence in FR-25 or DD-6.
2. **Should `NVIS_CONFIG_PROVENANCE_ALL=1` be named in AC-26?** As written, AC-26 is vacuous under
   DD-6's default scope — see the note on TC-31 — so the plan supplies the flag. If the intent was
   for the criterion to hold under the *default* scope, then either the scope or the criterion needs
   to change, because no secret key can reach the default block at all.
3. **Does the illustrative block in DD-6 want correcting?** Its line
   `NVIS-CONFIG RACK_NVSW_ADMIN_PASSWORD rung=overrides secret=1` cannot be produced under the
   scope rule stated four bullets below it (file keys plus FR-21's required set), only under
   `NVIS_CONFIG_PROVENANCE_ALL=1`. Same root cause as question 2; cosmetic on its own, but the
   example is what an implementer will copy.
4. **Where does TC-35's recorded baseline live, and on which machine?** AC-29 requires a *recorded*
   baseline; the plan writes it to `.plc/briefs/launch-configuration-evidence.jsonl` keyed by
   machine. This is the gap `oidc AC-23` left open and it should be settled before implementation
   rather than at first red run.
5. **Should a Docker-capable runner be requested for the pipeline?** It would collapse TC-39's two
   arms into one and remove Coverage Gap 1 outright. It is an infrastructure ask, not a code change,
   so it needs an owner.
6. **Does `ui_managed` want a requirement of its own?** The brief's *Backward coverage* names it as
   one of two design elements that are deliberately **not requirement-derived** ("records an
   existing security decision … it constrains no new behaviour"). But TC-34 shows it does constrain
   behaviour that matters: without `ui_managed=False` on `NVIS_GREENLIGHT_CONFIG`, one Settings save
   redirects the whole process's configuration to an operator-chosen file. The case is written and
   cited against FR-1a and FR-11, which is honest but indirect. Either a one-line Security FR or an
   explicit "verified without a requirement, by design" note would settle it — flagged rather than
   resolved here, because adding a requirement is not this document's job.
7. **Will a fresh deployment with no `greenlight.toml` and no exported `RACK_SSH_HOST` refuse to
   boot?** By the code as it stands, yes — and it is the one place NFR-8 and decision 3 pull against
   each other. `DEFAULT_EXEC_MODE = "ssh"` (`transport/factory.py:36`) makes the `RACK_SSH_HOST`
   predicate fire by default; on a first boot `seed.build_default_project_from_env` takes the host
   from the environment (`seed.py:578`) and `high_overlay` skips an empty value
   (`catalog/context.py:172-174,199`), so the seeded cluster carries nothing for the predicate to
   find and FR-18 refuses. That is decision 3 working exactly as designed, and it is *not* RG-1
   (the placement is right; the setting is genuinely absent). But NFR-8 says "the upgrade must be a
   no-op at every site until someone writes a file", and at any site relying on the SSH default
   without an explicit host it is an outage instead. Discovered while writing TC-27 clause (c),
   which is why that clause is scoped to `RACK_EXEC_MODE=local` and says so. Needs a ruling before
   implementation: either the predicate keys off an explicitly-configured connection rather than the
   resolved default, or NFR-8 acquires an exception naming this case.

### Assumptions and Unresolved Questions

1. **`tomli` is not installed anywhere in this workspace today** (verified 2026-09-03 in both the
   system interpreter and `.venv`). Entry criterion 3 exists because of it: TC-11, TC-13 and TC-40
   are unrunnable until DC-8's pin lands, and a first run before that will look like three failures
   rather than a missing prerequisite.
2. **`sys.modules[name] = None` raises `ModuleNotFoundError`**, not a bare `ImportError` — measured
   on Python 3.12.13 on 2026-09-03. TC-11 and TC-13 depend on this, because FR-4 mandates catching
   `ModuleNotFoundError` specifically and a mask producing a different exception would exercise a
   different idiom than the one specified.
3. **Fail-closed cases must run in a subprocess.** DC-3's refusals raise `SystemExit` at import;
   pytest catches it, so an in-process case would then assert "nothing was applied" against an
   interpreter the failed load had already touched. This is stated as an assumption because it
   constrains implementation, not just the plan.
4. **TC-3 row (b) and any mode assertion assume POSIX and a non-root uid.** The product deploys as a
   Linux container; root can read a mode-`0000` file regardless, so the row skips when
   `os.geteuid() == 0` — as AC-6 itself anticipates.
5. **TC-35 measures on a developer workstation**, as NFR-1 specifies. It is not a claim about the
   OVA under load.
6. **The frontend is untouched.** Decision 8 adds no endpoint and no UI, so no vitest case appears
   and `frontend/src` is not exercised.
7. **`route_snapshot.json` must not move.** Stated as Exit Criterion 3 rather than as a test case,
