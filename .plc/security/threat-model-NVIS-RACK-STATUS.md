### System Overview

This system is an operator console and management framework designed to validate, observe, and manage physical NVIDIA GB200/GB300 NVL72 AI-factory clusters. Human operators interact with a React-based frontend browser interface that communicates with a Flask backend container. The Flask backend acts as the central coordination hub, orchestrating workflows, running an autonomous AI agent, and translating operator requests into SSH commands executed on a Cluster Control Host (Head Node). The Control Host then relays these low-level hardware management and monitoring commands directly or indirectly to the physical target environment, which consists of Compute Trays, NVSwitches, and Baseboard Management Controllers (BMCs).

### Components

- **Operator Browser**: A client-side interface comprising a React 19 Single Page Application (SPA), a WebSocket Terminal, and the human operator, used to inspect fleet health, launch validation workloads, manage Slurm nodes, power-cycle trays, and open interactive shells.
- **Flask Backend (Application Layer)**: The central coordination hub and API gateway, shipped as a Docker container, that manages authentication, coordinates backend services, and acts as the sole software bridge to the Cluster Control Host, data stores, and external services.
- **Workflow Engine**: An internal backend service co-located with the Flask App that coordinates and executes multi-step validation or operational workflows consisting of arbitrary shell steps.
- **AI Agent Loop**: An internal backend service co-located with the Flask App that executes autonomous LLM tool-calling loops to invoke product actions.
- **Cluster Control Host (Head Node)**: A Linux host in the Infrastructure/Control Zone equipped with cluster management and access tools that serves as the primary execution layer and gateway for physical hardware management.
- **Compute Trays & NVSwitch BMCs (Target Environment)**: The physical hardware layer (comprising Compute Trays, NVSwitches, and BMCs) that executes low-level hardware commands such as power cycling, firmware updates, sensor reading, and password rotation.
- **TinyDB Catalog**: A local data store in the Data & Secrets Zone used by the Flask App to persist and retrieve catalog data.
- **SQLite Databases**: Relational databases in the Data & Secrets Zone used by the Flask App to persist and retrieve relational data, which internally depend on SSH Private Keys.
- **Encrypted Vault**: A local secret store in the Data & Secrets Zone used for secure storage and retrieval of secrets.
- **SSH Private Keys**: Mounted private keys in the Data & Secrets Zone utilized by the Flask App and Cluster Control Host to authenticate outbound SSH connections.
- **Grafana**: An external monitoring and visualization service used by the Flask App to query or push telemetry and metrics.
- **Prometheus**: An external monitoring and metrics collection service used by the Flask App to scrape targets or push metrics.
- **nvFTP**: An external file transfer service used for SFTP upload of artifacts, logs, or validation outputs.
- **NVIDIA Inference API**: An external service consumed by the AI Agent Loop to provide LLM inference capabilities.
- **Google Sheets**: An external service target for the Flask App (specific role and purpose unspecified).

### Interactions and Data Flow

- **Operator Browser -> Flask Backend**: Direct HTTP/WebSocket traffic carrying operator commands (validation workloads, node management, power control) and interactive terminal sessions, typically secured via an SSH tunnel.
- **Flask Backend <-> Workflow Engine**: Bidirectional internal calls carrying execution tasks and status updates.
- **Flask Backend <-> AI Agent Loop**: Direct internal co-location interactions carrying agent instructions and feedback loops.
- **Flask Backend -> Data & Secrets Zone (TinyDB, SQLite, Encrypted Vault, SSH Private Keys)**: Direct local file/database access to read/write catalogs, query databases, retrieve secrets, and read mounted SSH keys.
- **Flask Backend -> Cluster Control Host**: Direct SSH connection authenticated via mounted private keys to relay cluster management commands.
- **Cluster Control Host -> Compute Trays & NVSwitch BMCs**: Direct or relayed (via Head Node as proxy) SSH/Management protocols (IPMI, Redfish, vendor CLIs) carrying hardware management and monitoring commands (e.g., power cycling, password rewrites, sensor reading).
- **AI Agent Loop -> NVIDIA Inference API**: Direct HTTPS/API calls carrying inference requests for LLM tool-calling.
- **Flask Backend -> Grafana / Prometheus**: Direct HTTPS/API calls carrying telemetry and metrics.
- **Flask Backend -> nvFTP**: Direct SFTP upload carrying file transfers (artifacts, logs, validation outputs).
- **Flask Backend -> Google Sheets**: Direct interaction (protocol and payload unspecified).
- **SQLite Databases -> SSH Private Keys**: Internal dependency where databases use/provide SSH private keys.

### Security Controls and Trust Boundaries

- **Trust Boundaries**:
  - **Operator Browser -> Flask App**: Distinct boundary, typically traversed via an SSH tunnel (`ssh -L 5156:localhost:5056`), making the browser origin `localhost`.
  - **Flask App -> Cluster Control Host**: Distinct boundary; the Flask App does not talk directly to hardware and must go through the Control Host.
  - **Strict Trust Boundary Architecture**: Separates the Operator, Application Layer, Control Host, Hardware Targets, Secrets Storage, and External Services.
- **Authentication**:
  - **Operator Browser to Flask App**: Authenticated via a Shared Bearer Token (`RACK_WEB_AUTH_TOKEN` in containers) or Host PAM (when running on the target host).
  - **Flask App to Cluster Control Host**: Authenticated via mounted SSH private keys.
  - **Cluster Control Host to Compute Trays/BMCs**: Authenticated via mounted SSH private keys.
- **Encryption / Transport Security**:
  - **SSH Tunneling**: Typically used to secure Operator Browser to Flask App traffic.
  - **SSH Protocol**: Used for Flask App -> Cluster Control Host.
  - **SSH / Management Protocols**: IPMI, Redfish, or vendor-specific CLIs over SSH used for Control Host -> Hardware.
  - **SFTP**: Used for nvFTP file transfers.
  - **HTTPS/API**: Used for Grafana, Prometheus, and NVIDIA Inference API.
  - **Encrypted Vault**: Used for storing secrets.
- **Secrets Handling**:
  - **Mounted SSH Private Keys**: Stored on the Control Host's filesystem (likely mounted by the Flask App/deployment mechanism at startup) to authenticate outbound connections to target hardware.

### Constraints and Assumptions

- **No Authorization Model (RBAC/ABAC)**: Any authenticated Operator has full root-equivalent capability on the Control Host and hardware (e.g., draining nodes, power-cycling trays, rewriting BMC/NVSwitch passwords, running arbitrary shell steps, opening root shells).
- **No Audit Trail Attribution**: Actions are not logged per-user.
- **Secret Exposure Risk**: The Control Host holds mounted SSH private keys providing root/admin access to all hardware; compromise of the Control Host or Flask App process equals total infrastructure compromise.
- **Single Session Flag**: Authentication relies on a single stateless session flag (`session["rack_web_auth"] = "1"`) with no user accounts, subjects, or roles.
- **Network Topology Gaps**: Network topology details (VLANs, subnets, firewalls) beyond the SSH tunnel are absent.
- **Database Schema Gaps**: Specific schemas for TinyDB, SQLite, or Vault contents are absent.
- **High Availability Gaps**: Failure modes and High Availability architecture for the Flask App or Control Host are absent.
- **Google Sheets Integration Gaps**: No protocol, data type, or purpose is documented for the Google Sheets integration.
- **Control Host to Secrets Zone Interaction**: Not explicitly documented; keys are assumed to be mounted into the filesystem rather than actively queried at runtime.

## Reviewer notes — two rows contradict shipped controls

The engine assesses each connection against a retrieved slice of the input document, and on this
run it missed two controls the input explicitly stated. Both are **implemented**, so treat the
corresponding rows as retrieval misses rather than residual risk:

- **`/ws/terminal` "missing Origin header validation"** (High / Very High impact). Origin
  validation *is* enforced — `web_auth.wsgi_origin_allowed()`, called from
  `_WebSocketTerminalMiddleware._refuse_reason()` before the path is claimed, configured by
  `RACK_WEB_ALLOWED_ORIGINS`. The engine's own metadata says "it does not mention any
  implementation of Origin header validation", which is a statement about its context window,
  not about the code.
- **"binds to 0.0.0.0 without TLS"** (High / Very High impact). `docker-compose.yml` publishes on
  `127.0.0.1` by default (`RACK_WEB_BIND_ADDR`), and TLS with a 1.2 floor is available on both
  servers. The engine's metadata again says the binding configuration "is not explicitly
  documented" in the context it retrieved.

This is the same class of limitation that produced T-19 in the 2026-08-19 run ("script-execution
API → root RCE"), a threat that does not describe this codebase at all. The engine is only as
accurate as the slice of context it retrieves per connection; rows must be reconciled against the
code before they are treated as findings.

- **Critical: 2 → 0.** Both August Criticals were the unauthenticated `/ws/terminal`. The
  remaining terminal rows are cross-site WebSocket hijacking (addressed, see above) and
  connection-count DoS (genuinely open).
- **High: 17 → 25**, driven by a more detailed input document rather than new defects: many new
  High rows are "a *compromised* Flask app abuses its SSH trust" scenarios, which presuppose
  prior compromise.
- **Requirements: 133 → 144** (39 → 45 mandatory).
- Still genuinely open and consistent with the recorded assessment: no authorization model, no
